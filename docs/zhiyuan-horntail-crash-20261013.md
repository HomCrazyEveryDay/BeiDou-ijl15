# 纸鸢逐风 / 蔡徐坤：10 月 12 日晚射手村异常退出

调查日期：2026-10-13。输入为玩家提供的 `logs(纸鸢逐风靠近黑龙输出，掉线).zip` 和错误截图。首两轮分析附件、本地源码、正式二进制备份及此前保存的生产日志快照。12:27 的续查增加生产只读 SELECT/资源核对，12:36 增加商城首次异常采样并构建、同步本地 DLL，详见文末交付记录。全程没有启动游戏或写生产，没有提交、推送、线上发布。

## 结论

用户随后明确：没有进入商城，靠近黑龙即闪退，且当晚多人发生。后续以同地图 Boss 战的共同上游为主线；单份转储中的商城分类调用链不能代表玩家主动进入商城，更不能作为这批事故的必要触发条件。第四轮已用与正式 1.0.34 哈希一致的实际资源，复现旧外观代码在游戏分配器下的堆损坏，并完成修复版对照，详见文末。

附件直接证实客户端异常退出。22:35:52～23:05:10（玩家时钟，北京时间）的 15 个异常运行，按同一 `clientRunId + connectionId` 与生产关闭连接记录精确关联：**纸鸢逐风 14 次、蔡徐坤 1 次，均为频道 1、射手村 `100000000`**。这些运行全部已包含在[射手村群体事故调查](henesys-boss-disconnect-investigation-20261013.md)的 193 个关联运行中，不能再次累加为新增受影响人数或次数。

截图的 `-2147467261` 对应 `0x80004003`，本附件确有六次 `_com_error(80004003)` 逃出主循环。并非每次都是该错误：还有 PCOM 工厂错误、资源查询错误、Canvas/图层空对象访问，以及一次商城商品分类校验终止异常。已定位直接失败位置，**尚未证明这 15 次具有同一个上游根因，也不能报告现有修复已根治它们**。

继续分析旧 DLL 静态地址和转储中的全局变量后，确认 PID 23652、9152 在崩溃前已初始化 `MixedDye::Images()` 缓存，且同进程 PCOM 使用游戏字符串分配器。这使已复现的资源字符串分配器错配与本附件建立了更具体的运行关联；但缓存条目、首次错误释放和写入者仍未保留，结论不能升级为根因闭环。

远离黑龙并不排除角色动作、地图内其他角色或公共 UI 的资源处理；蔡徐坤实际失败于角色动作加载中的 Property 工厂。因此“不参与输出仍退出”与已有证据并不矛盾。不过，附件没有角色位置/完整画面重放，不能独立核实其与黑龙距离，也不足以确认固定十分钟周期。

## 新附件补充的具体定位

### Boss 血条背景查询

PID 32384 的近期异常链为 `80030002 → EXE 00403AF7 → 0053377B → ijl15+10AEA → 00533315`。正式 EXE 在 `00533747` 取得 StringPool `0xCD8`，其内容为 `UI/UIWindow.img/MobGage/backgrnd`；`00533776` 调用资源查询包装器，返回位置正是 `0053377B`。

这是 Boss 背景查询失败，与前批附件的 `UI/StatusBar.img/gauge/graduation` 查询失败属于不同具体调用点。实际请求文本和资源管理器内部状态没有保留，路径是静态调用规定的期望值，不能把它写成已恢复的现场字符串。

四次 `80004003` 的近期异常栈经过 BossHP 包装器调用原生 `CField::ShowMobHpTag`。源码与正式 DLL 对应关系显示，异常发生在原生调用返回之前，后面的自定义百分比计算尚未执行。栈上出现 BossHP hook 本身不能证明百分比算法有错。

### 蔡徐坤也发生资源工厂错误

PID 16104：`PCOM+52CF/+4E67 → EXE 0041A8CA → 00412DF4 → 0041283C`，与 PID 9368 的 Property 工厂栈一致。调用代码期望创建 `Property`；实际类名、PCOM 内置分支自身句柄和最初坏值没有被该旧构建保存。不能据此认定 PCOM.dll 缺失、角色必为龙神，或某个出现在栈上的动作 hook 已被证明写坏内存。

### 状态栏刻度的空 Canvas

PID 23652 的 main-loop / targeted dump 保留原始上下文：`Canvas+ED28` 执行 `mov eax,[esi]`，`ESI=ECX=0`，读取地址 0。Copy 参数为 `x=218, y=544, source=0`。原始栈保留 `008DA3EE`，对应 `UI/StatusBar.img/gauge/graduation` 的调用位置。PID 30148、26408 的文本帧也经过状态栏 `008D824C`，但它们的原始 dump 已不在附件中，不冒充逐个恢复到了相同局部变量。

### 背包物品图标的空 Canvas

PID 9152 的 main-loop dump 记录 `Gr2D_DX8+7998` 读取地址 0，`ESI=ECX=0`。原始链为 `Gr2D+AC1A → EXE 00426C10 → ijl15+127E5 → EXE 0081D5D1`，InsertCanvas 的 canvas 参数为 0。

正式 EXE 在 `0081D553` 调用 `CItemInfo::GetItemIconCanvas(005D3BD8)`，将输出 `[ebp-10]` 在 `0081D5C5` 传给 InsertCanvas。继续展开所属原生函数 `0081D42E`：该分支响应鼠标按下 `0x201`，坐标 `(65,132)`，创建拖动物品的图标层；此次 `useIcon=0, disabled=0`，已经请求原始图标。因此仅给 `useIcon=1` 增加 iconRaw 回退不能覆盖这个现场。

原生帧与正式 DLL 包装器的保存寄存器布局共同保留了物品对象 `0x29B1D3DC`；局部槽位值为 10，但背包类型页未保存。较大的最终未处理 dump 保留该物品对象及加密 ID 指针 `0x2C0B5430`，后者指向的存储页没有被转储捕获，不能可靠还原物品 ID。此次已收窄到“开始拖动背包物品时得到空图标”，仍缺具体物品和上游查询结果。

DLL `+127E5` 是既有 InsertDreamCanvas 包装器调用原函数后的返回点，不能只凭该帧认定梦境缩放已执行。也不能因为同为 `Gr2D+7998` 就套用历史磁石失败动画结论。

### 原生终止异常属于商城分类初始化

PID 11548 的 `22000006` 原始抛出返回点为 `004722C7`，上层为 `00468411 → 00776B17 → 00776001`。继续展开函数 `00471F37` 后，已定位为商城构造函数调用的商品分类初始化（此调用链本身不证明玩家主动进行了进入商城操作）：

- `00472107` 使用 StringPool `0x569`，静态资源名为 `Etc/Category.img`；`00481806` 将分类构造成每项 `0x1C` 字节的数组，挂在商城对象 `+0x44`。
- `004721C7` 调用 `00A25DB4` 读取商城封包内容，随后遍历上下文 `+0x36E0` 的商品数组。堆栈残留中的操作码 `0x7F` 也与服务端 `SET_CASH_SHOP` 一致；该残留不是完整原始封包。
- 对 `10,000,000 <= SN < 80,000,000` 的商品，原生代码计算 `Category=(SN/10,000,000)%10`、`Sub=(SN/100,000)%100`（整数除法），再用 `00471BB5` 查找对应分类。
- 查找返回 -1 时，`004722AA～004722C2` 抛出 `22000006`。这是本次抛出分支的确定条件，但最初的商品 SN、实际分类数组和封包缓冲区没有保留，尚不能判断来自玩家磁盘资源、服务端动态覆盖，还是运行内存异常。

已使用 workspace 的 `tools/xml-img-patcher.ps1 dump-xml` 只读反导出本地客户端 Category / Commodity，与服务端 XML 比较：两侧均为 30 个分类、9,004 条商品。Commodity 所有节点一致，Category 只有 `/Category.img/6/Name` 文本不同；按上述原生公式检查，9,004 条商品均无缺失分类。此检查只覆盖当前本地资源，不代表玩家当晚 IMG 或生产数据库动态商品覆盖也已核验。

服务端 `PacketCreator.openCashShop` 会把 `MonthlyShopService.cashOverrides` 的商品覆盖写入封包；其中还包含 `modified_cash_item` 数据库内容，因此仅比较 Commodity XML/IMG 不足以排除封包侧因素。没有用资源表校验通过宣称整个商城正常。

该分支不是此前宠物 fly 零帧的 `00703E1C` 栈；不将它直接归为已修复的宠物 UOL 问题，也不将其与其余 COM/Canvas 异常强行合并。
