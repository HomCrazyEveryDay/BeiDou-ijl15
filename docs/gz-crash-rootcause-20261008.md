# 玩家崩溃逐案复核与 gz 日志深查（2026-10-08）

接续 [退出前触发原因续查](exit-trigger-investigation-20261008.md)。用户提供的是分别发生的崩溃日志和 dump，没有声称玩家同时掉线。本轮回读会话“分析最近崩溃日志”，重新确认四个附件及原始请求；不以同一玩家、地址或时间接近代替同一次运行的证据。

## 本轮结论

1. 四包中 27 份 `004031FE` 及纸鸢逐风那份 `KERNEL32+1EB0B`，都能恢复出 **CRT 在 WinMain 返回后调用 exit(0)** 的外层栈布局。此前把所有这类报告描述成“先异常掉线、再二次崩溃”过于确定。证据只能确认进入退出清理；用户关闭游戏、已处理的异常/断线、程序自行退出仍需区分。
2. 原 33 份近期 `004031FE` 中有 20 次的最后接收包为 `0xDF`。原生客户端的上下文清理也会生成该包，服务端仅注销组队搜索，不在这个处理器中踢人。它不能作为“组队功能引发崩溃”的证据，也不能当作用户主动关闭的证明。
3. 找到两份有明确服务端退出分支的登录阶段样本：账号 716、691，均由 `AcceptToSHandler` 的第 24 行断开，随后退出清理崩溃。这是已识别的前置断开路径，但日志没有记录条款选择字节，不能判定是拒绝、无效数据或条款状态不匹配，更不能据当前账号角色推定当次操作人。
4. 心跳超时必须区分先后。糖果是甜的 10 月 7 日及祝福19号同日的崩溃，分别早于服务端超时约 81 秒、47 秒；这两次不能倒因为果地归咎于心跳踢人。糖果是甜的 10 月 5 日、忆气 10 月 7 日则分别在断开约 2 小时 12 分、2 小时 43 分后才生成退出崩溃。
5. 月神冰、梨涡允允的指定 `004031FE`，Fibonacci 两次，以及纸鸢逐风 10 月 5 日的两类退出样本，仍没有能唯一确定初始退出动作/异常的证据。未据此改动玩法、背包、资源、踢人或心跳策略。

## 新恢复的 exit(0) 外层证据

原 EXE 基线 `timestamp=4B7C15C9`：

```text
00A640CE call 009F19F2    ; WinMain
00A640D3 mov [ebp-60h],eax
00A640D6 push eax
00A640D7 call 00A637E2   ; CRT exit
00A637E2 push 0
00A637E4 push 0
00A637E6 push [esp+0Ch]  ; 转发 exit code
00A637EA call 00A63822   ; 执行退出回调及清理
```

27 份 PCOM dump 加纸鸢逐风系统 DLL dump 均有：

```text
0019FEE4  00A637EF       ; 内层返回位置
0019FEE8  00000000       ; exit code
0019FEEC  00000000       ; quick
0019FEF0  00000000       ; return-to-caller
0019FEF4  00A640DC       ; 外层返回位置
0019FEF8  00000000       ; WinMain 返回值传入的 exit code
```

相邻两层返回位置、参数数量与间距相互对应，不只是“堆栈里搜到某个像代码的数”。四份非退出故障 dump 没有这一组合。此处代码页未保存在这些小 dump 中，调用指令来自已核对 PE 基线，不能声称读取到了玩家现场完整 CRT 代码。

`exitCode=0` 是最终析构崩溃前的退出参数，不是监控器最终观察到的进程退出码；后者仍会因真实访问异常成为 `C0000005`。WinMain 可以在处理过内部异常后返回 0，故这个结果也不证明玩家亲手关闭了窗口。

额外检查所有 32 份 MemoryInfoStream：27 份 PCOM 在捕获时的低 2 GiB 空闲地址空间最少仍有约 1082 MiB，最小的最大连续空闲区约 83.5 MiB。最终现场不呈现地址空间耗尽；但这些 dump 在清理后取得，不能据此排除清理前曾短暂内存不足。

## 0xDF 的因果方向

原生 `00A3E2D7` 使用 `COutPacket` 构造并发送 opcode 223 (`0xDF`)。它的调用者包含 `00A120E7`；上下文批量清理在 `00A047D8` 调用后者，该函数清空搜索状态再发包。另有界面操作和状态更新调用者，所以不能从“发出了这个包”反推用户动作。

生产服务端 `PartySearchUpdateHandler.handlePacket` 调用 `unregisterPartyLeader`，后者移除搜索队列/设置，不直接关闭会话。20 次 PCOM 最后包为它，与退出清理可生成该包的事实一致。不能按“最后一包”原则修错处理器。

## 额外发现：心跳写入未完成的另一类断开

全保留范围共有 189 条 `ping-timeout`，其中 19 条的本次 ping 尚无成功写入记录。纸鸢逐风 **10-08 05:03:22** 的另一运行 `fa8b7913db6118626eb54ddbc6f0ba13`（connection 22898）属于此类：

- `pingSubmittedAt=05:03:07.497`，超时时 `pingWrittenAt=0`、`lastPongAt=0`；最后接收游戏包是 05:00:20.790。
- 服务端关闭后 1 ms，未完成写入收到 `StacklessClosedChannelException`。
- 生产代码确实从提交 ping 时开始 15 秒计时，并没有等待写成功。此记录可证明“提交后未完成心跳响应”，不能表述成“已把 ping 发给客户端而客户端拒绝回复”。
- 写不完可能是连接已无进展或发送缓冲积压，现有日志不足以区分；不能据此断言改长超时就能恢复网络。没有这次运行对应的已提供 dump，不能拿它解释 10 月 5 日两份崩溃。

这是一条独立且真实的服务端诊断线索。若后续修复心跳状态机，应分别约束写入期限与写成功后的响应期限，并保留明确的发送停滞原因；本轮没有用这种诊断改进冒充已修复玩家客户端崩溃。
