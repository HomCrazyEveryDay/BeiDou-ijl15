# 死亡提示框恢复与最小诊断

日期：2026-09-30。背景和证据见 [原故障排查](death-dialog-investigation-20260930.md)。用户已授权先修复可验证的卡住状态，并保留下次故障的关键记录。该实现修复已证实的缺计时状态，不代表已经确定原玩家的自然触发来源。

## 行为

- 原生死亡动作、封包、HP、死亡效果、窗口单例和复活选择均保持原流程，不再包含人工制造故障的代码。旧 `[DeathDialogTest] Mode=1` 不再被读取。
- 在客户端自己的 `CWvsContext::Update` 返回后，每 500 ms 读取本机角色、HP、死亡姿势、死亡效果、待执行计时和窗口单例。HP 的读取验证原生 TSecType 校验值；读取不可信时不恢复。
- 仅当 HP=0、死亡姿势与效果都存在，且连续 3000 ms 没有待执行计时、没有弹窗时，调用原生 `00A066F3` 补设一次计时。原生更新在计时超过 2200 ms 后自行构造窗口，因此缺计时场景预计在死亡后约 5～6 秒出现提示框。正常死亡仍使用原有延迟。
- 每次死亡只补一次。原生已经尝试创建窗口、玩家选择复活/回村、上下文重置/切图之后不再次补设。构造失败留证，不由本恢复逻辑循环创建。瞬时读取失败不会忘记已选择复活的状态；HP 恢复后才允许新的死亡周期。
- 所有动作调用参数原样转发；不改变诱惑等状态、不替玩家选择复活、不发送回城封包。原生窗口继续决定普通回村、道具复活或灵魂之石提示。

默认配置，无需为玩家新增配置文件：

```ini
[DeathDialog]
Recovery=1
Logging=1
```

`Recovery=0` 仅关闭补计时，保留记录；`Logging=0` 仅关闭记录，补救仍生效；两者都关闭才不安装钩子。安装时校验动作、更新、窗口创建/取消、原生补计时及本地动作包装函数的机器码，部分安装失败时回滚。

## 最小日志

沿用 `logs/ijl15-lifecycle-*.log`，不新增逐包/逐帧日志或独立后台线程。启动一条 `event=death_dialog_install ... version=2`；正常死亡通常只有动作前后、窗口创建前后和取消前后几条记录。异常才增加补救、10 秒超时或异常现场记录。

每条含死亡周期号、HP、姿势、逻辑时钟、计时及年龄、窗口/效果状态、是否已补救/尝试创建/关闭，以及调用地址。原生 `0094A10A` 包装函数的外层返回地址另记为 `origin`，解决原先只能看到中转地址 `0094A11A` 的问题。补救、异常取消和异常记录附最多 12 个返回地址；创建/动作异常额外记录异常代码、故障地址，并继续传播给原生异常处理。

| phase | 可判定的阶段 |
| --- | --- |
| `action_before` / `action_after` | 首次死亡的原始 force、实际来源，以及动作执行后是否已有计时 |
| `observed_dead` | 没有从动作入口开始追踪，但更新中发现了本机死亡状态 |
| `recover_missing_timer` / `recover_scheduled` | 缺计时持续超过阈值，补设前后的状态 |
| `create_before` / `create_after` / `create_failed` | 原生是否尝试创建窗口，是否返回对象与单例 |
| `cancel_before` / `cancel_after` | 谁清除了计时/窗口，是否发生在窗口创建前 |
| `create_exception` / `action_exception` | 原生调用未正常返回的异常代码、位置与栈 |
| `state_unavailable` | 校验/读取失败，已主动禁止恢复 |
| `timeout` | 死亡追踪超过 10 秒仍没有窗口；每次死亡只记一次 |

不记录账号凭据、聊天或封包内容。每小时最多 256 条普通记录和 64 条异常记录，分别计额并按小时恢复，防止普通死亡耗光后续异常的额度，也避免每帧刷日志。假如达到上限，应结合启动时记录的限额解释日志覆盖，不能把未出现某条记录当成对应事件绝对没有发生。极端高频异常、日志磁盘写入失败或进程在落盘前被强制结束仍可能影响取证；不能承诺所有故障都能仅凭这些记录确定完整根因。

## 验证与交付

`tests/DeathDialogDiagnosticsTest.ps1` 编译实际 C++ 钩子，使用参考 EXE 的入口签名及替代的原生依赖。验证正常死亡不改变、强制首次死亡缺计时的单次恢复、HP/效果/本机角色保护、取消/切图/选择后的抑制、读取失败后保持关闭状态、新死亡周期、原生异常记录与透传、旧实验开关失效、配置独立开关、时钟回绕及日志额度恢复。

workspace 的 `tools/death-dialog-probe/tests/native-flow-check.py` 直接执行参考 EXE 的死亡分派、补计时及计时到期机器码，验证补计时后遵守原生 2200 ms 阈值、不覆盖已有计时，并用 7 个 HP 值交叉核对读取算法与原生解码器。图形渲染和窗口构造仍为替代依赖，不是完整实机验收。

DLL 使用 `Release|x86` 构建；客户端关闭后同步 `out/Release/ijl15.dll` 到本地 `BeiDou-Client/ijl15.dll` 并核对 SHA-256。最终实机行为由用户手动验证：用本地 `ZhuMengLauncher-Dev.exe` 启动，在黑龙死亡后等待至少 10 秒，确认提示框出现并可正常选择回村。若仍异常，保留对应 lifecycle 日志。不要再次打开旧人工实验开关；本版本不存在注入行为。

生产服务器无需加载这项 DLL 修改；本轮不涉及服务端、WZ/IMG 或生产部署，也不自动启动或操作客户端。

本轮交付结果：上述 C++ 回归与 8 组原生指令检查通过，`Release|x86` 构建及构建附带的启动器父进程规则检查通过，仅有既存的 Detours PDB 缺失链接警告。确认客户端关闭后已同步本地 DLL，构建产物与客户端文件均为 589312 字节，SHA-256 均为 `1B8CC065BC895188097691861AD881CC43E78FC63D49C02F29A74F02F0985C65`。本地配置为 `Recovery=1, Logging=1`；旧实验 DLL 仅备份在忽略的诊断目录。尚待用户实机验收，未提交或向玩家发布。
