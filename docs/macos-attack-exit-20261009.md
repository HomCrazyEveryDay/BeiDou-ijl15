## 11:12 Wine 11.18 卡死现场

用户再次反馈卡死，进程仍存活，macOS PID=4588，Wine 游戏 PID=396，客户端会话 `20261009-030706708Z-pid396`。最初 `ps` 显示 CPU=202%，内存实际占用约 480 MiB；退出日志只有 monitor_ready。日志、5 秒 sample、vmmap 和 LLDB 只读线程/寄存器/内存片段已保存至 workspace `_diagnostics/macos-hang-20261009-1112/`。调试器采样后已 detach，没有终止、重开或操作游戏。

与上轮相比，这次线程名称可以确认：故障发生在 Wine 的 `wined3d_cs`（Wine tid=`01c0`），主线程为 `0190`。LLDB 的临时线程序号会变，按线程名称选择，不能固定使用 #8/#9。音频 mixer 线程等待在系统调用，没有证据把卡死归因于音频。

原始信号上下文位于保存的 `signal-context.bin`，EXCEPTION_RECORD 位于 `exception-record.bin`，解析结果为 `signal-context.json`：

- `RIP=7BF21135`、`CS=0107`、`RSP=02D50020`、`RBP=0365FF50`；异常码 `C0000005`，读地址 `00002EC5`。
- 11.18 的模块映射确认 wow64cpu 基址 `7BF20000`，RVA `1135` 的机器码为 `8B 15 C5 2E 00 00`，仍是 64 位模式下的 RIP 相对读取；实际低地址 `2EC5` 与在 32 位模式执行该字节序列吻合。
- 原始异常之后，Wine `setup_raise_exception` 保存异常记录。LLDB 停在 `memmove`，目标 `RDI=02D4FEF0`；vmmap 显示 `[02D41000,02D50000)` 为无权限保留区。二次故障发生在 Wine 异常保存过程中，解释了为什么客户端日志没有收到正常异常报告，也不能把 memmove 当作最初业务错误。
- 调试器已读到原始记录，不能再仅依据 sample 中重复的 ntdll 栈帧推断递归深度；Rosetta 混合栈的自动展开存在重复伪帧。

该故障与 11.0 后台线程在 wow64cpu 读取低地址的模式一致，但仍未证明最早是谁改变了执行状态。没有通过修改技能、伤害或禁用音效掩盖问题。

同时发现运行时差异：11.18 加载客户端原生 `l3codeca.acm`，11.0 曾加载 builtin；当前卡死堆栈不支持把该差异作为根因，因此本轮没有改音频后端。

### 针对当前线程的规避验证

独立 x86 D3D8 程序在单独测试 prefix 创建隐藏窗口和硬件 device，分别执行 120 次 Clear/Present：`csmt=1` 时枚举到 1 个 `wined3d_cs` 线程；`csmt=0` 时为 0，两轮均退出码 0。8 线程宿主调用测试约 30 秒完成 4856522 次调用，没有复现同样异常。两者是边界明确的 API 测试，不能代替游戏实机验证。
