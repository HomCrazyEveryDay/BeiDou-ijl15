## 原始故障位置与对象

核对分析二进制：`BeiDou.exe` timestamp `4B7C15C9` / SizeOfImage `00A94000`，`PCOM.dll` timestamp `4B7C140C` / SizeOfImage `00025000`。未强行加载不匹配的 ijl15 PDB。

原生释放函数入口 `004031ED` 已检查传入指针非空；真正出错指令是：

```asm
004031F2 mov ebx, [ebp+8]  ; 待释放指针
004031F5 test ebx, ebx
004031FC je 00403243       ; 空指针直接返回
004031FE mov eax, [ebx-4]  ; 读取分配块头部，发生 AV
```

最新样本中：

- 字符串持有对象位于 `03F92E0C`，内容指针为 `01336228`，引用计数已经递减到 0。
- PCOM `+2AB6` 析构函数将内容指针减 4，即 `01336224`，传给全局 Free 回调。
- 回调槽 `50C212B0` 实际为 EXE 的 `009F2514`，即导出函数 `ZtlTaskMemFreeImp`。
- 导出函数以 `ECX=00BF0B00` 调用 `004031ED`；`004031FE` 再读取 `[01336224-4]`，即不可访问的 `01336220`。

这不是直接由某个地图画布渲染指令触发的空指针，也不是 PCOM 代码已经被卸载。此时 PCOM 模块仍在，失效的是所依赖的数据内存。

## 调用链与 List.wz 的关联

首次异常栈保存了以下连续返回地址，已逐项用调用点反汇编交叉核对：

```text
PCOM DLL 进程退出回调 / CRT 析构循环
  → PCOM+6C23：全局对象 50C21480 的析构入口
  → PCOM+7484 / +7810：遍历并清空表
  → PCOM+7C4F / +7CC6：删除表节点、释放 node+8 的字符串对象
  → PCOM+2A85：引用计数递减
  → PCOM+2AB6：调用字符串内存释放回调（返回点 +2AC9）
  → BeiDou!ZtlTaskMemFreeImp（009F2514，返回点 009F2522）
  → 004031ED：ZAllocEx<ZAllocAnonSelector>::Free
  → 004031FE：读取失效分配头部
```

全局对象 `50C21480` 由 `PCOM+6BF8` 懒初始化，并注册 `PCOM+6C23` 为退出析构回调。其构造函数 `PCOM+6C3A` 拼接模块目录下的 `List.wz`（只读 `rb`）、读取并解码字符串，然后插入该表。其使用者位于 WZ 字符串序列化路径。这使“PCOM 字符串表”定位进一步具体到 List 表，并不证明 `List.wz` 文件内容损坏；本次没有修改或重建资源。

最终 unhandled dump 的 EIP 已到 `PCOM+1049F`，属于异常展开后的现场；不能把该 EIP 或调试器就近显示的 `PcSerializeString+...` 当成真实故障函数名。原始异常位置和调用关系以首次异常 dump 为准。

## 原生内存池已进入析构的证据

原生匿名分配器 `00BF0B00` 的静态析构回调为 `00796D51`：

```asm
00796D51 test byte ptr [00BF00F0], 1
00796D58 jne 00796D6B
00796D5A or byte ptr [00BF00F0], 1
00796D61 mov ecx, 00BF0B00
00796D66 jmp 00797B64
```

`00797B64` 遍历对象 `+1C` 起的四条内存池块链，调用 `00797BCD`；后者减去块头后调用 `GetProcessHeap` / `HeapFree`。这不是只减少一个业务对象引用计数，而是销毁整个分配器的池块。析构后未清空这些链表字段，所以 dump 中仍有非零池指针并不代表池仍然有效。

在全部 4 份配对最终 dump 中，`[00BF00F0]=0000001F`，其中 bit 0 正是该析构入口设置的标志。EXE 中该字节的其余直接引用属于邻近几个静态对象析构位；没有找到该 bit 的其他正常置位路径。同时，PCOM 的 Alloc/Realloc/Free 槽仍为 `009F2503 / 009F2525 / 009F2514`。

## 续查：离线析构顺序对照

续查日期：2026-10-08。临时探针位于 `../../.tmp/exit-4031fe-probe/`；构建的是独立的 `probe.exe`，不是客户端 DLL。探针不执行游戏入口、不加载 `ijl15.dll`，不连接服务器。输入为当前客户端的 `BeiDou.exe`、`PCOM.dll`、`List.wz`；矩阵执行前后也核对了 `ijl15.dll`，四个文件 SHA-256 均未变化，完整哈希保存在 `probe-matrix.json`。

探针把 EXE 的内存映像放在独立进程的不同基址，并对实际使用的分配器指令做有限重定位；PCOM 由系统正常加载。因测试基址比原地址高 `0x30000000`，实验故障地址 `304031FE` 对应游戏内 `004031FE`，不是另一条故障指令。使用前核对 EXE 和 PCOM 的 PE timestamp、映像大小。

分配器底层使用三种模式对照：

- `guard`：分配后在释放时撤销页面提交，确定性暴露后续失效读取。它改变底层页面回收方式，因此不能把此模式的必现率当成游戏实际崩溃率。
- `audit`：使用 Windows 进程堆，记录每个池块分配/释放；只在临时探针中跳过已确认失效的释放回调，以数完所有失效调用。该模式的 `fault=0` 不是修复成功，也不代表原调用安全。
- `heap`：使用 Windows 进程堆正常执行释放，作为正确清理顺序的对照，不跳过释放回调。

所有实验均从真实 `List.wz` 加载 371 条记录。未调用 PcInitModule 的基础组使用 25 个原生池块；完整初始化组使用 26 个，其中 `PcTermModule` 正常释放额外的模块路径字符串，但仍保留 List 表全部 371 条。

| 对照条件 | 结果 | 支持的结论 |
| --- | --- | --- |
| 先销毁池，再析构 List，`guard` | 第一次字符串释放即发生 `C0000005 @ 304031FE` | 可以复现原故障指令 |
| 同样顺序，`audit` | 371 次 List 释放全部落入已释放池块 | 失效引用不是只存在于单条字符串 |
| 先调用 `PcTermModule`，再销毁池、析构 List | `PcTermModule` 后仍有 371 条；`guard` 同位置异常，`audit` 仍计到 371 次失效回调 | 只提前调用模块终止函数不足以修复 |
| 先析构 List，再销毁池，最后再次析构 List，`guard` / `heap` | 371 条正常释放、表清空、全部池块正常释放、0 次失效回调、无异常 | 调整依赖清理顺序能消除本实验中的故障；空表再次析构可行 |
| 先成功执行 `PcInitModule`、加载 List，再 `PcTermModule`，随后分别测试上述两种顺序 | 错误顺序仍异常；正确顺序在 `guard` / `heap` 下均无异常 | 结论不依赖省略 PCOM 正常初始化/终止 |

`run_matrix.py` 共验证 10 个组合，每项均校验预期的异常位置、失效回调数量、表项数和池块释放数，并保存各自原始输出。10 项断言通过表示预期观测成立；其中故意使用错误顺序的 `guard` 组本来就应触发异常，不是“10 项游戏验收通过”。基础组正常清理发生 371 次 Free 回调，完整初始化组发生 372 次；多出的 1 次来自模块路径字符串。

## 续查：修复时机与限制

原生退出路径进一步确认：`00796D45` 把分配器析构回调 `00796D51` 注册给 EXE 的退出回调机制；退出路径 `00A63873` 起倒序执行回调，随后才在 `00A638BF` 调用 IAT `00AF0118`（已解析为 `KERNEL32.dll!ExitProcess`）。返回地址 `00A638C5` 与日志一致。证据见 `crt-before-exitprocess.asm.txt`。

所以对这条已观察到的正常 CRT 退出路径，仅在现有 `DisconnectDiagnostics.cpp` 的 `ExitProcessObserved` 中追加 List 清理已经太晚：原生分配器的退出回调位于它之前。不能因为日志中的 `process_exit_requested` 早于最终异常，就推断该观察点仍早于内存池销毁。

具体实现应在分配器开始销毁之前安排 List 清理，并继续让原生分配器正常完成析构。落地前需要满足：

1. 校验实际 EXE/PCOM 版本、目标入口和 List 已初始化状态；退出时不能为了清理而首次初始化 List。
2. 确认之后不会再读取或重新填充 List，核对正常关闭、连接失败关闭、异常结束等实际退出分支，以及其他持有原生分配器内存的 PCOM 对象。
3. 原有 PCOM 后续析构应只面对已清空的表；重复清理的离线对照已通过，但完整进程的其他对象仍待验证。
4. 保留正常运行期的释放行为和异常捕获。实验中的 audit 跳过逻辑不能进入交付 DLL，也不能把吞掉最终异常作为修复。

这些证据把“析构顺序”从 dump 支持的解释推进到可控条件下复现的原因；并未证明全部线上同地址事件同因，也未解释最初断线/退出原因。其后实现、构建与同步已完成，完整关闭/换线/连接失败的实机验收仍由用户执行。

## 实施与验证

### 实现范围

- `ezorsia/PcomExitFix.cpp` 在原生分配器静态析构入口接入清理顺序修复。调用 PCOM 原有 List 析构函数后，继续执行原生分配器析构；不修改普通 Alloc/Free，不延迟或跳过整池释放。
- `RefreshRateTrace.cpp` 在现有原生资源/图形工厂返回且 PCOM pin 成功后安装。安装校验 EXE/PCOM 的 PE 版本、映像大小、相关指令以及 Alloc/Realloc/Free 回调，版本或实现不匹配时记录原因并不安装。
- 分配器已析构时，重复调用直接保留原生空操作；List 未初始化时不调用懒加载入口。清理前再次核对分配器回调。PCOM 随后注册的原始析构回调保留，只会面对已经清空的表。
- 退出日志使用已有 `ClientLog::Emergency`，每次析构最多记录三条，无逐帧/逐包开销。不吞异常；List 清理若抛异常，不继续释放其依赖的池块，交由原有异常捕获处理。
