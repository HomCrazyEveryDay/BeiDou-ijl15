# Write.dll 多功能辅助特征与 RichEdit 退出崩溃排查

记录日期：2026-10-13。来源：玩家 `logs(9).zip`、后补 `Write(1).zip`，以及 2026-10-13 对附件的静态分析、dump 比对和对应客户端调用链核查。

本文用于后续识别同类样本、区分退出阶段的二次崩溃与最初故障，不是自动封禁规则。只对下述已核实文件及代码版本作明确归因；其他版本需要重新核对。没有运行该辅助、启动游戏或验证停用后的实机结果。

## 已确认的结论

附件是一份含“弓不挥拳”选项的多功能游戏修改辅助，同时包含内存改写、断点和向量异常处理器逻辑。其内嵌 ExUI 界面库与 4 份当前 RichEdit 崩溃 dump 的捕获代码完全匹配，处在文本控件销毁时的致命调用链上。

**不能把同一玩家的全部闪退归因于该辅助。** 本案多次先出现游戏主循环异常，再在清理阶段发生 ExUI/RichEdit 崩溃。仍需查清前一个异常；辅助存在也不能替代 BeiDou 自身修复和发布验收。

文件中包含某项功能，不等于玩家当时启用了它，也不证明该功能在当前游戏版本有效。本文识别的是游戏修改辅助及其故障特征，不宣称完成了盗号、木马等行为审计。

“弓不挥拳”的 GBK 控件名在原文件偏移 `001348F4`，UTF-16LE 显示文字在 `00134998`。其他版本不可直接套用这些偏移。

本版本还确认了以下机制，均为静态证据或已捕获数据，不是动态演示：

- `Write+1AAF4` 分派补丁安装/恢复；安装逻辑保存原字节、写入 `CC` 软件断点并维护补丁表。
- 存在内存保护修改及 `rep movsb` 写目标内存的路径。
- `Write+49A88` 注册/移除向量异常处理器，入口为 `Write+4B435`，再进入内部异常分派。
- 4 份当前退出 dump 中，`Write+40A414` 的处理句柄全局非零，`Write+40A418` 的业务回调均为实际 Write 基址加 `35660`。这些是已初始化状态的证据，不能代替 Windows 处理器链的完整枚举。
- `Write+40A260` 的版本选择值为 `53`（十进制 83）。

补丁表的堆指针在部分 dump 中尚存，所指堆内容却未被捕获；新附件也没有配置。因此无法可靠恢复玩家实际勾选列表。即使只开一个功能，其界面库及公共框架也可能已经初始化。

## RichEdit 崩溃识别

### 此案的精确签名

系统模块的匹配身份：

| 字段 | 值 |
| --- | --- |
| Msftedit PE TimeDateStamp / SizeOfImage | `7E21C2CA` / `002A7000` |
| 匹配 PDB GUID / Age | `A7BBA1A6-BC8F-9DB1-526F-E025348D90A0` / `1` |
| 故障 | `C0000005`，读地址 0，`Msftedit+6B1D7` |
| 匹配微软符号 | `CW32System::GlobalRelease+93` |
| 现场状态 | `ESI=0`；`g_pIClipboard=0`；`CW32System::_cRefs=0` |

调用链：

```text
ExUI 控件销毁分派（返回位置 +6CB3E）
  → 控件清理（返回位置 +A28A4）
  → CTxtWinHost_Etit 析构
  → +9C0B0 调用文本对象 Release（返回位置 +9C0B3）
  → CTxtEdit::Release / CUnknown::Release
  → CTxtEdit 析构
  → CW32System::GlobalRelease
  → 读取为空的 g_pIClipboard
  → Msftedit+6B1D7 崩溃
```

如果使用从故障点向外的 EBP 帧顺序，私有库三个返回 RVA 顺序为 **`9C0B3 → A28A4 → 6CB3E`**。这是库基址相对偏移，不是固定虚拟地址；跨进程应先确定各自分配基址并处理 ASLR。

有效原生帧中对应的 RichEdit 返回 RVA 为 `67E76 → 67B2D → 678BD → 9E4AB → 9E0D1 → 9E2B2 → 9E202`。不同系统 Msftedit 版本必须重新匹配符号，不应只凭 `6B1D7` 数字强行归类。

### 证据强度

- 4 份当晚保留的 RichEdit dump：内嵌 PE 按实际私有区域基址重定位后，每份 7 个代码区域、7,168 字节全部相同，包含上述三个关键返回点附近代码。外层 Write.dll 身份和数据关系亦匹配，**直接调用组件归属已确认**。
- 9 个当晚会话的文本报告：故障模块/偏移、有效帧及三个私有返回位置的相对关系均一致。其中 4 个有上面的二进制核对，另外 5 个只能报告“文本特征一致”，不能称为做过同样的逐字节验证。
- 全附件另包含历史记录：54 个不同哈希 dump 中，48 个位于同一 RichEdit 故障地址，48 个均加载同身份字段的 Write.dll；43 个有足够内存区元数据可核对相同私有帧模式，另外 5 个缺该元数据。**48 是包含历史的 dump 数，不是当晚闪退次数或已去重事件数。**

同版 Msftedit 的 `OnDllProcessDetach` 会清零 `g_pIClipboard`。因此“RichEdit 全局清理早于辅助最后一个文本对象释放”是最有力的生命周期解释；静态快照未记录所有历史写入及卸载事件，仍不能宣称完整时序已动态重放，也没有完成修复实测。

## 2026-10-12 晚逐次归因范围

这里统计附件可还原的 **14 次进程退出记录**，不是声称 14 次全部发生在正常游玩中。时间范围以报告内部时间和运行 ID 关联；本玩家时钟比服务器快约 13 分 17～18 秒，跨端应先按 connectionId 对齐。

| 可确认的顺序 | 运行数 | 本案 PID | 应如何表述 |
| --- | ---: | --- | --- |
| 先有主循环异常，后有同类 RichEdit 崩溃 | 7 | 13604、12636、19856、18548、2440、13592、15056 | 存在退出阶段二次崩溃，最初异常仍须独立追查 |
| 有同类 RichEdit 崩溃，未捕获此前主循环异常 | 2 | 15068、5464 | 5464 明确先 WM_QUIT / normal_return；15068 为何开始退出证据不足 |
| 有主循环异常，未记录同类 RichEdit 崩溃 | 3 | 1676、12560、9592 | 分别为暴击 Canvas 空源、Property 工厂错误、龙王血条 E_POINTER |
| 异常退出但未能明确故障位置 | 2 | 11392、18952 | 前者退出码 CFFFFFFF；后者先正常退出流程、最终 C0000005，均缺足够现场 |

因此：9 次有同类 RichEdit 特征，10 次有主循环异常，两者重叠 7 次，**不能相加成 19 次闪退，更不能把 9 次退出异常全当成首次原因**。

例如 PID 15056，先在龙王 `8810018` 的原生血条处理中抛出 `80004003`，约 4 秒后才在辅助文本控件释放过程中出现 RichEdit 访问违例。辅助清理修复或停用后，前面的血条异常是否消失仍需验证。

PID 1676、12560、9592 的主循环 dump 模块表没有列出 Write.dll。缺少模块记录不证明进程从未运行过任何外部代码，但这些样本不支持“所有故障都已归因于 Write”的结论。尤其不能用退出组件问题覆盖以下已存在的待查项：

- 暴击 `Effect/BasicEff.img/NoCri1/effect` 空 Canvas 经过原生 `00438225` 直接 Copy，漏过既有两处防护；对象为何为空仍未知。
- 三次龙王血条 E_POINTER 均恢复出怪物 `8810018`、颜色 3/5、最大 HP 2090000000，但内部第一次失败的对象操作未捕获。
- PCOM `800401F8` 的相同抛出位置可由内置模块句柄异常或类加载失败产生，不能直接宣称玩家缺 DLL。
- 当时玩家加载发布版 1.0.34，部分后续 PCOM/本地防护改动未进入其构建；本地修好不等于现场已验收。

跨设备同场景的其他证据见 [射手村 Boss 活动调查](henesys-boss-disconnect-investigation-20261013.md)。那是另一组样本，不能把本文件匹配结论扩展成“其他设备也使用同一辅助”。

## 后续排查流程

1. 先保存原附件、日志、dump 和文件哈希；按运行 ID 合并首机会、主循环、退出清理、监控记录。只统计最晚一份 dump 容易遗漏最初故障。
2. 核对文件指纹和模块完整名称。只读检查可用 `Get-FileHash -Algorithm SHA256 -LiteralPath '<样本路径>'`、`Get-AuthenticodeSignature -LiteralPath '<样本路径>'`；不要为了识别而运行未知 DLL。
3. 匹配本版本 RichEdit 和 ExUI 调用链。优先使用有效帧、内存区属性、实际代码比对；`exception_stack_candidate` 等原始栈地址候选不等于有效回溯。
4. 把结论分为“文件/模块命中”“同类退出特征”“直接组件调用链确认”“最初故障已定位”。存在某个辅助不自动完成最后一级归因。
5. 需要对照时，由玩家完全停用该辅助，用官方文件及正式启动器启动新进程，覆盖正常退出、暴击和龙王血条。只取消某个选项不能排除已加载的界面框架；操作客户端仍遵守工作区实机验证规则。
6. 若停用后最初故障仍出现，继续调查对应资源/COM/调用点；不能以“之前发现外挂”结束案件。若只消失 RichEdit 尾部异常，应报告退出阶段问题得到隔离，而非全部根治。

当前没有修改辅助，也没有上线检测、封禁或自动删除规则。应由辅助作者检查文本控件/COM 对象销毁与界面库卸载顺序；BeiDou 的剩余异常和补丁交付分别验收。
