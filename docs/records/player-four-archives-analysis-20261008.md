## 证据边界

32 份 dump 的异常流均存在，但 `CONTEXT.EIP` 都已不在 `ExceptionAddress`，且此前全栈扫描没有找到通过校验的原始故障 CONTEXT 副本。因此下文的调用链是**捕获内存中的残留帧、参数、全局字段，加上本地同版本代码核对**，不是完整的首次异常调用栈。

实际捕获到的怪物、物品读取及焦点故障指令与 EXE 基线一致；较远调用点的代码页有缺失，逐处以 `captured=null` 记录，不能声称所有玩家运行时代码都已校验。系统模块故障指令则由同次 dump 直接取得。

文件名中的时间是进程会话开始时间，`timestamp=` 才是崩溃报告时间。下文事件时间换算为 UTC+8。本次范围固定为四包，不是重新扫描全部后台日志或新一轮用户实测日志。

## 1. 系统模块异常实际位于退出清理链

样本：`logs(6).zip` 中 pid25800、tid5096，run=`87d488625fa359c359a1edff44d33fcd`，报告时间 **2026-10-05 10:57:43.297（UTC+8）**。这是此前纸鸢逐风样本的同次 dump。

该 dump 的 KERNEL32 基址 `77080000`，PE timestamp `869878D1`，image size `000F0000`；模块流版本记为 `6.2.19041.6456`。参考完整 dump 的版本字符串为 `10.0.19041.6456`，不能把字符串差异抹掉；两者 timestamp/size 和本次捕获的函数指令相符。同构建参考导出表将 `+1EB00` 命名为 `InterlockedDecrement`，EXE 对应 IAT `00AF0188` 的导入名称也相同。

同次机器码：`+1EB08 or eax,-1`，`+1EB0B lock xadd [ecx],eax`。目标 `248B3120` 所在页面 `248B3000..248B5FFF` 为 `MEM_RESERVE`、保护值 0，所属 allocation base=`24120000`；这不是正常可写的已提交对象页。

更关键的是三组证据同时对应：

1. 全局 `CWvsContext` 位于 `00BF1C20`，`+3680` 的引用槽地址 `00BF52A0`，其中 `+4` 保存 `248B3114`。释放函数 `00A16222` 对这个对象的 `+0C` 递减引用计数，恰好得到异常目标 `248B3120`。
2. 残留栈的 `0019FE98` 保存返回 `00A1623D`，后一字即参数 `248B3120`；随后依次是引用槽 `00BF52A0`、返回 `00A15319`、全局对象 `00BF1C20`、返回 `00A02893`。
3. 更外层保留 `00A6387B`，是 CRT 倒序执行退出回调后的返回位置。静态代码也明确把 `00A01C71 → 00A026A7` 注册为 `00BF1C20` 的退出析构，`00A0288E` 正好释放 `+3680` 成员。析构 SEH 状态残留为 `0x41`，与该成员的原代码一致。

所以应将此前“切图上下文中的系统 DLL 写异常”收窄并纠正为：**客户端已进入原生退出清理时，释放 CWvsContext 持有的窗口引用，计数地址已经无效。** 服务端当时仍在地图切换只说明连接状态，不能决定客户端最终异常发生在哪个阶段，也不能解释最初为什么进入退出。

`+3680` 的对象来自 `006CD6BA` 构造，原生分配大小 `0x150`；正常释放路径 `00A043FC..00A04411` 先调用 `CWnd::Destroy(009E00AF)`，再释放引用。尚未恢复是谁提前销毁/释放该对象、是否漏清槽位、是否有其他内存损坏。按现有证据不进一步猜具体 UI 名称。

该现场 `00BF00F0=0`，PCOM 修复所等待的原生池析构尚未执行；与 27 份 `004031FE` 的 `00BF00F0=1F` 明显不同。当前 `PcomExitFix` 在更后的池析构入口清空 List，不能据此认为会修复此处。后续应跟踪上述成员的建立、Destroy、替换及释放顺序，保留首次异常；不应在 `InterlockedDecrement` 全局吞掉错误。

## 2. 物品异常：红龙宠物刷新先删除了空槽

样本：`logs.rar` 中 pid21188，run=`dde240b1f9b1f78c5b308efd1e5c8314`，报告时间 **2026-09-30 15:19:32.023（UTC+8）**，旧 DLL=`6ABB6245`。

故障是 `00428743 mov eax,[ecx+8]`；报告 `ECX=0000000C`、访问地址 `00000014`。残留返回地址 `00A1ECFA` 对应 `00A1ECF5 → 0042873D`，上层在库存删除分支取得物品指针后，未经空值检查就访问 `item+0C` 的物品 ID。

父帧 `0019D9FC` 中物品指针为 0、库存类型为 5；参数指向 `CInPacket=0019DAC8`。它的缓冲区 `253C15EC` 和长度 73 均被 dump 捕获，读取游标为 12，正好停在第一项删除的四字节操作信息之后：

| 字段 | 从同次内存恢复的值 |
| --- | --- |
| opcode | `0x001D INVENTORY_OPERATION` |
| updateTick / 操作数 | 1 / 2 |
| 第 1 项 | mode=3，CASH=5，slot=24，删除旧物品 |
| 第 2 项 | mode=0，CASH=5，slot=24，重新加入物品 |
| 新物品 | itemType=3（宠物），itemId=5000031（默认 String/Pet 中为 Red Dragon） |

封包总长与文本末条 `opcode=0x001D size=73` 一致；这次崩溃还没执行到第二项添加。现金栏数组所在页未包含在 dump，不能声称已逐格读取背包；“旧对象为空”来自捕获帧、故障寄存器及实际调用点的互证。

当前服务端 `Character.forceUpdateItem` 仍用“mode 3 + mode 0”刷新物品；宠物喂食/属性变化等调用会经过它，后台在线物品修改也有同样封包形状。仅凭封包不能唯一指定是哪一个调用者，也不能推定是红龙 IMG 资源有问题。更早的库存不同步、重复移除、跨切图刷新或槽位变动时序仍待核对。

未发现现有 DLL 修复覆盖 `00A1ECC2..00A1ECFA` 这条删除空物品路径。后续调查应同时检查服务端刷新与库存变更顺序、宠物 ID/槽位一致性和客户端重新同步；只让通用物品 ID getter 对空值返回 0，会影响大量正常调用并掩盖库存分歧。

## 3. 焦点异常：角色选择按钮返回后使用旧窗口

样本：`logs(6).zip` 中 pid12768，run=`fddaea56a4d5fd94eb5a49eec7add415`，报告时间 **2026-10-02 09:56:46.218（UTC+8）**，旧 DLL=`6ABB6245`。

`009E3275` 取传入窗口接口的虚表，`009E327E call [eax+48h]` 访问失败；报告 EAX=0，访问地址=48。残留帧保留：

- 直接返回 `006016CD`，对应 `006016C8 → CWndMan::SetFocus(009E3264)`；参数为 `1F1FA670`，与保存的 ESI/ECX 相同。
- 外层 `0042445E`、`004C10E9` 与按钮派发一致，button ID=`1002`。
- 原生回调 `00601667` 对 button 1002 调用 `005F7C4A`（项目 `Client::DeleteChar` 已将该入口定义为角色删除），返回后无条件尝试对原窗口 `self+4` 设置焦点。

这支持“角色选择按钮的操作返回后使用了失效窗口”这条具体路径，但完整首次异常 CONTEXT 已丢失，不能把残留帧等同完整玩家操作录像。dump 捕获时该原窗口地址已是 UTF-16 路径内容，说明更晚读取到的内存已经不同于崩溃瞬间；不能把这段路径的所属输入法/诊断模块直接当作释放者或罪因。

已有 `22c1abf` 四职业取消修复涉及 `CRaceSelect::OnCreate/OnDestroy` 和取消创建流程，解决提前 SetFocus 重复登记窗口。这次已恢复的直接调用者却是 `00601667` 的角色选择按钮回调；现有实现没有对这个回调做生命周期处理。当前材料不足以宣布前一修复已覆盖本例，也不应对 SetFocus 统一跳过所有坏指针。继续定位要关注操作/弹窗期间的消息重入、场景改变及旧窗口是否仍存活。

## 4. 已有两项修复的现场匹配

27 份 `004031FE` 均读取到 `00BF00F0=1F`（池析构 bit 0 已置位）、PCOM 模块内释放返回地址，以及 `009F2522` 的原生 Free 返回位置。它们都发生在旧版 DLL 上，新增样本支持 [PCOM 清理顺序调查](exit-004031fe-investigation-20261008.md)；没有提供新修复安装后的反例。

两份 `0066B5B1` 分别来自 10 月 4 日 pid20384 和 10 月 5 日 pid13840。后者就是原调查的 run=`52bdd31b590ca704e2876e0ff1bc86be`。读取结果：
