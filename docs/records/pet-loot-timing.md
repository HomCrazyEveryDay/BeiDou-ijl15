# 掉落物静态拾取属性缓存与诊断

## 原因与修复

GMS 083 原生 0x005D5224 通过资源接口查询道具 info/pickUpBlock 并返回布尔值。该结果取决于静态道具资源，不取决于角色、地图、距离或掉落实例。大量掉落导致客户端反复查询同一属性，拖慢更新。

现场第二版探针捕获：扫描外查询每两秒耗时约 1980–1988ms，掉落物池更新单次最高 152.691ms。只缓存宠物拾取扫描不足以解决问题，最终修复对该属性函数所有调用入口统一缓存。

每线程固定 4096 槽位，以资源提供者和道具 ID 校验；冲突重新查询，异常不缓存，不持有 WZ 对象。不改变拾取权限、距离、归属、宠物过滤或背包判断。运行期间 WZ 资源应保持不变，更换资源后重启客户端。

## 配置

客户端程序目录的 pet-loot-timing.ini：

```ini
[debug]
enablePetLootCache=1
enablePetLootTiming=0
```

缓存默认开启，诊断默认关闭；更改后重启。缓存设为 0 可恢复原始查询。该配置独立于启动器管理的 config.ini。不要额外开启旧逐异常监控。

## 可选诊断

开启 enablePetLootTiming 后，logs/ijl15-trace-*.log 的启动标记为 probeVersion=3，缓存标记 scope=all_property_callers。入口签名不匹配或安装失败时不启用本组功能。每两秒由后台线程输出七行汇总，十分钟自动停止计时，缓存继续生效；每次启动约 2103 行以内，不逐物品写日志，不强制刷盘，不记录封包正文。游戏回调只计时与原子统计。

- pet_update：原生宠物更新耗时，包含拾取扫描。
- pickup_scan：原生拾取扫描耗时。
- pickup_property：扫描内属性查询耗时，含缓存查询。
- property_outside_scan：扫描外同一属性查询耗时，也使用缓存。
- drop_update：原生掉落物池更新耗时。
- drop_update_gap：同一线程、同一池两次更新开始的间隔，不等于渲染帧耗时；切图或暂停也可能增大。
- pet_loot_cache：缓存命中和未命中次数，不代表掉落物数量。

calls、totalMs、maxMs 分别为窗口次数、累计和最大单次时间；嵌套耗时不能相加。无锁交换为近似统计，边界计数与耗时可能落入相邻窗口。探针有少量开销，不支持运行时卸载 DLL。

## 验证与交付

x86 独立测试覆盖缓存复用、冲突、异常后重试、禁用缓存、扫描内外共用缓存、ABI 参数与返回值、异常透传、禁用计时、计数重置及掉落物更新间隔。Release|x86 构建成功，本地主分支 DLL 同步到客户端并核对 SHA-256。

2026-09-21 用户反馈第三版“可以了，不卡了”，现场功能验证通过；修复后的量化耗时日志尚未提供。证据针对掉落物场景，不据此断言龙咆哮异常诊断问题也已解决。

旧启动器 2.0.6 的实测包基于 5284389，仅加入同一缓存和探针；当前主分支产物用于新版启动器，两种 DLL 不可混用。旧版测试包和日志不提交。
