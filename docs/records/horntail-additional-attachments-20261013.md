## 深入对照：修正堆策略差异，保留未闭环结论

### 独立探针与游戏的默认策略不同

正式 `BeiDou.exe` 的 PE OS / subsystem 版本是 4.0，原探针的 subsystem 版本为 6.0。Microsoft 说明：32 位 EXE 的 subsystem 主版本至少为 6 时，默认启用检测到堆损坏即终止；DLL 的 subsystem 版本不控制该策略。见 [Microsoft 原文](https://devblogs.microsoft.com/oldnewthing/20131227-00/?p=2243/)。因此“使用了游戏原分配器”不等于整个探针进程的堆策略与游戏相同。

只调整独立探针副本的 PE OS / subsystem 版本为 4.0，保持代码和资源输入不变，旧版和修复版均完成 21 次构建、25,600 次 UI 读取。旧版分配池块达到 5,356，修复版为 1,303。旧版原本的 `C0000374` 是有效的错误释放证据，但不能直接替代现场 `E_POINTER / VT_EMPTY` 的因果证明。玩家进程是否另有组件显式启用过终止策略没有捕获；这里只对齐 EXE 默认条件，没有声称完全复制玩家进程。没有修改实际游戏 EXE 或 Windows 全局设置。

证据：`legacy-policy-results.json`、`.tmp/horntail-legacy-policy-20261013.py`。

## 15:18 续查：资源缓存生命周期及 hitAfter 取证缺口

### 缓存释放与保留的父对象

核对本地正式 EXE / ResMan 后确认，资源管理器 vtable `+0x24`（`ResMan+3DCE`）接收一个缓存年龄参数，并分别清理两类缓存；`+0x18` 是另一种资源操作，不能按清缓存接口调用。原生 EXE 在 `00529326` 传入 `180000`，在 `0064291F / 0064298A` 传入 `0`。`180000` 是条目年龄门槛，不能据此宣布游戏每三分钟执行一次，也不能解释用户所说的固定十分钟。
