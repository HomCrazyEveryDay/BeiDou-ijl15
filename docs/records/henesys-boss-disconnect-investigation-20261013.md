# 2026-10-12 晚射手村集中掉线调查

调查日期：2026-10-13。起点为玩家提供的 `ZhuMeng-diagnostics-20261012-221516(1).zip`，进一步只读核对生产业务日志、日志站上传文本及正式发布二进制。二次调查额外编译并运行了隔离的 x86 组件探针；未修改业务代码、客户端资源、DLL 或生产状态，未启动游戏、构建交付 DLL、提交或推送。

## 结论及可信边界

这次已经确认是 **1 线射手村 Boss 活动时段集中出现的客户端异常**。证据覆盖多台设备，不能归结为附件玩家单机网络不稳定。客户端的资源/COM 对象读取、创建和绘制在多个位置失败，异常进入游戏主循环或最终访问违例；服务端随后记录连接关闭，其中大多数为连接重置。

**直接故障机制已定位，共同上游根因尚未闭环。** 城镇召唤 Boss、集中同屏场景与故障的关联很强，但现有证据不能进一步断言是哪一个怪物、技能、外观、资源加载操作或 DLL hook 首先破坏了状态。不能把空指针保护当作该场群体事故已经根治，也不能把全部不同地址的异常强行合并成一个已证实的代码缺陷。

**二次深挖推进到实际参数语义：** 唯一的 `80070057` 样本已经定位到字体样式解析器的“非法字符”分支，原生调用处应传入 StringPool `0x583 = BA`。另外8次PCOM故障的调用点全部完成映射：6次原本创建 `Shape2D#Vector2D`，2次原本创建 `Property`。这些是运行时基础参数/对象状态异常的重要线索；目前优先排查字符串传递、缓存及对象生命周期，但尚未抓到首次错误写入，不能宣布“内存踩踏已坐实”。

### 影响范围

- 附件设备在玩家时钟 22:09:45～22:37:33 有 **26 个不同运行实例**捕获到异常；压缩包导出后的部分由日志站补齐。按故障连接精确关联：勇气 21 次、桃气 5 次，均为频道 1、地图 `100000000`。不是按设备/IP推断角色，也没有把同一运行中的历史角色当成故障角色。
- 全站异常文本与生产关闭连接记录按 `connectionId` 交叉：服务器时钟 **22:08:58～23:07:28，193 个异常运行，31 个设备标识、40 个角色**，均关联频道 1 射手村。设备标识不等于人数。
- 同场景 22:00～23:15 的业务日志有 245 次非转场关闭记录，涉及 50 个角色。这不是 245 次已确认崩溃：仅以上 193 个运行有配套异常文本。
- 对193个运行，187条关闭原因是 `network_exception:SocketException:Connection reset`，6条是没有记录到服务端请求的 transport close。不能仅因最终 `reason=server` 就认定服务器主动踢人；该标签也来自服务端捕获 socket reset 后的清理。

### 客户端时钟偏差

附件设备的 UTC 时间转换为北京时间后，比服务器约快 **29.10～29.13秒**。该值由同一 `connectionId` 的客户端 `diagnostic_binding` 与服务端 `context-bound` 配对得到，包含少量网络往返/调度误差。

例如 pid87648 首机会为玩家时钟22:13:42.524，按绑定偏差换算约为服务器22:13:13.4；服务器22:13:16.490才记录reset。因此不应把未经校时的服务器22:13:16与玩家22:13:42直接比较，然后倒推“先断网、后崩溃”。

## 附件设备的26次异常分类

每次运行只计一次；首机会、主循环、最终未处理快照不重复累加。

| 直接异常 | 运行数 | 已有定位 |
|---|---:|---|
| `_com_error / 80004003` | 11 | 空对象/指针错误，多条涉及原生 Boss 血条、角色或怪物绘制 |
| `_com_error / 800401F8` | 8 | PCOM对象创建时取得的模块句柄为空；需区分外部加载与内置类分支 |
| `C0000005 / Canvas+ED28` | 4 | 空源画布进入Copy；附件含其中两次的原始dump |
| `_com_error / 80030002` | 2 | ResMan资源路径查找失败，包括状态栏刻度图 |
| `_com_error / 80070057` | 1 | 原生工具提示字体创建中，样式字符串命中非法字符分支 |

这些不是“五种互相无关的问题已经全部定位到源头”。错误分散在几个原本应正常工作的系统资源路径，优先需要追资源/COM异常的共同上游。

### 1. 两次空画布是状态栏 graduation，不是历史 percent 样本

pid50500、pid87648 的首机会与主循环dump一致，CDB独立复核pid87648：

```text
EIP=5000ED28: mov eax,[esi]
ESI=0, ECX=0，访问地址0
原生Copy返回地址=008DA3EE（CALL位于008DA3E9）
绘制坐标 x=218, y=544，source=0
绘制帧 EBP=0019EAC8，[EBP-A0]=0
```

正式EXE的控制流明确：`008DA270` 获取StringPool `0x96F`，即 `UI/StatusBar.img/gauge/graduation`；查询/Canvas转换结果保存在`[EBP-A0]`，随后在`008DA3E9`传入Copy。这不是旧报告中`008DA86E`的`number/percent`路径，也不是左括号。

正式1.0.34 `Data/UI/StatusBar.img` 本轮通过orange-wz反读，确有`gauge/graduation` Canvas节点，文件135373字节、SHA-256 `9c2b5a31d14bb1554e3d6a811f0a0fbdd545b55ecae67b8b58af8c59bea971e3`。这证明正式对象结构可读，不代表附件玩家磁盘IMG已核验；附件没有IMG原文件。本轮未重新对该节点做像素解码。

两份dump已经能证明空源Copy致命路径，但未保留最初查询的完整键名、HRESULT、资源管理器内部字典和加载流，不能据此选择“磁盘缺节点”“查询返回空”“接口转换不成功”中的某一种作为已证实源头。

### 2. 22:14:34对应同一刻度路径明确返回80030002

pid86052原始异常栈为：

```text
_com_error(80030002)
→ EXE 00403AF7（ResMan查询包装）
→ EXE 008DA297
→ EXE 008D824C（状态栏绘制）
```

`008DA297`是查询`UI/StatusBar.img/gauge/graduation`之后的返回点。这把部分调查从“Copy最后为空”推进到“更早的ResMan查询已失败”。错误码是资源/存储查找失败，不足以证明物理磁盘上整张StatusBar.img不存在。

### 3. Boss血条路径的空对象不能直接归咎于自定义百分比显示

pid81408保留`ijl15+10AEA ← EXE 00533315 ← EXE 005313FF`。正式1.0.34 DLL反汇编与源码对应 `BossHP::HookShowMobHPTag` 调用原生`005336CA / CField::ShowMobHpTag`。

`+10AEA`是原生调用后的返回地址，自定义`DrawBossHpNumber`还没有执行。因此不能仅因栈上有BossHP hook就认定自定义百分比计算或绘制造成异常，也不能声称此前修过BossHP页面权限就覆盖本问题。

全站193个关联运行中，有62个E_POINTER样本的近期异常栈保留新/旧构建对应的原生Boss血条包装位置。近期异常不一定是最终错误的唯一原因，但该路径是优先补充上游采集的位置。

### 4. PCOM模块加载失败，需要真正的路径和Win32错误

8个该设备运行以`800401F8`逃出主循环，近期原始异常均保留 `PCOM+52CF ← PCOM+4E67`。正式PCOM在`+52AE`检查模块句柄，零值会在`+52CA`抛异常，返回位置正是`+52CF`。**这个共同出口并不保证8次全都执行过LoadLibraryA**：普通类经`+5284`加载组件；内置`Property/List/UOL`则从`PCOM+1CA24`取自身模块句柄，再汇入同一检查。

二次调查按正式EXE反汇编与StringPool常量逐个核对：

| 原本应创建的类 | 运行数 | 原生调用证据 |
|---|---:|---|
| `Shape2D#Vector2D` | 6 | StringPool `0x3BE`，创建包装返回`00447F80`，上层返回`004410FF`或`0043FF62` |
| `Property` | 2 | StringPool `0x3BD`，创建包装返回`0041A8CA`，上层返回`00412DF4` |

这里的类名是**调用代码规定的期望值，不是从异常现场恢复到的实际字符串**。Property样本还经过正式DLL `+48886`，已对应`EvanRuntime::MountBodyTraceGate`调用原生身体动作加载器`0041272C`；原生函数内部随后创建Property。该hook对所有经过该调用点的角色动作均可出现在栈上，只有指定龙神骑宠和爬梯/绳动作才改变动作参数，不能据此认定故障角色必为龙神或认定hook已经越界写入。

现有dump没有覆盖该次加载的DLL路径字符串，也没有保留失败瞬间的GetLastError。现场模块表已包含Canvas、Shape2D、PCOM、ResMan等主要模块，不能用这个错误码笼统断言“PCOM.dll丢失”，更不能据此要求重装Windows或显卡驱动。

隔离进程使用正式组件，分别以正确名称创建Vector2D、Font、Property各1000次，全部成功。受控改为`Shape2DTYPO#Vector2D`和`PropertyTYPO`，均复现 `800401F8 / PCOM+52CF`，并捕获错误模块名及Win32错误126。该实验只证明**名称异常可以产生完全相同的分支**，不证明玩家现场名称就是这些值；Property真实名称未变但自身句柄异常等情况仍须现场证据区分。成功LoadLibrary后的非零LastError是残留值，不当作加载失败。

### 5. 字体异常已精确到样式字符串含非法字符

pid78440近期同tick异常链为`Canvas+4685/+5939/+30EC → EXE 00463453 → 008E4CC3`，随后`80070057`逃出主循环。二次反汇编明确区分三个输入：StringPool `0x582 = Canvas#Font`为类名，`0x1597 = Arial`为字体名，`0x583 = BA`为样式。原生`008E4C67`起取得BA并创建BSTR VARIANT，接着以字号12、颜色-1调用字体创建接口。

Canvas `+45C5`解析的是样式VARIANT，大小写不敏感地接受`A/B/I/N/S/U`。无法取得字符串时从`+4609`抛异常，其返回位置是`+460E`；**样本实际是`+4685`，对应`+4680`的非法字符异常**。因此，该次调用在解析器内部已读到了样式允许范围之外的字符，不能解释为Arial字体不存在，也不是已经走到字体/GDI资源分配失败。

用正式Canvas运行隔离探针：`BA`、`ba`均返回标志17，空字符串返回0；受控输入`BA?`与`Arial`均产生 `E06D7363 / 80070057 / Canvas+4685`，与现场分支一致。`BA?`、`Arial`是实验输入，**不是玩家dump中读出的异常样式文本**。

该证据足以将本例收窄为“原本应为BA的样式参数在解析时不合法”。尚不能区分StringPool输出已错、BSTR/VARIANT传递或生命周期错误、共享缓存/堆内存被更早操作破坏。当前源码StringPool汉化hook未发现针对这些类名、BA、Arial或graduation路径的直接替换；这不等于已排除其他hook的间接影响。

### 6. 正式Boss血条资源存在，但玩家现场资源仍未核验

从测试发布服务器只读取得1.0.34清单锁定的`Data/UI/UIWindow.img`，大小11813463字节、SHA-256 `cb67494a2fdf32cf5620985516c33e0fc6e7765a5e1fa72248a489285b5fe252`，用orange-wz成功反读。`MobGage/backgrnd`至`backgrnd4`、`Mob/8800000`、`Mob/8810018`、`Gage/1/0`、`Gage/1/1`均有Canvas节点。原生Boss血条反汇编使用这些路径族；现场封包记录没有原始payload，不能断言每次实际mobId和血条配色索引。

这降低了“正式包根本没有扎昆/黑龙血条节点”的可能性，但不是玩家磁盘哈希、像素解码或原生加载兼容性验证。实验性独立ResMan探针未复刻游戏完整资源初始化，读取GMS IMG时得到异常类名及800401F8；其输出单独保存为`native-proof-resource-incomplete.txt`，**不作为正式IMG损坏、玩家类名乱码或原生读取验证通过的证据**。通过的实验仅限基础对象工厂和字体样式分支。

### 7. 现有dump为什么无法继续还原最早输入

已逐一检查标准内存流和自定义`BDS1`附加块，而非只看文本栈：

- 字体及PCOM样本的mini-targeted dump主要保存主循环再次抛出时的栈、少量代码及异常记录；原始函数参数所指向的堆内存未收录。主循环再抛出时，前面具体资源/字体调用已退栈。
- pid86052的查询帧仍可得到BSTR holder地址`323E7020`及ResMan对象`307C3C00`，但两个地址指向的内存均不在dump中。查询输出VARIANT为VT_EMPTY，不足以恢复实际请求键名。
- 两份较大的Canvas未处理dump能读到StringPool全局对象和缓存数组指针，但目标数组项及其字符串页不在已保存范围。`deep-stringpool.json`中的null表示**未捕获/无法读取**，不是现场值为零。

因此，现有证据能确定“哪里失败、失败属于什么参数或对象”，不能恢复首次坏值及写入者。继续反汇编可以列出候选机制，不能补出从未保存的内存字节。

## 跨设备证据

193个精确关联的运行中：106个为E_POINTER、38个为800401F8、18个为80030002、1个为80070057；24个逃逸记录未解码为C++类型，另有1个CTerminateException与5个无可匹配逃逸类型记录。按首份异常代码为166个C++异常、27个访问违例。不同分类角度不应相加。

其中160个加载DLL标记`6ACA6C26`，33个为`6AC7FAE5`。资源/COM异常同时存在于两种构建，不能把本场全部归因于最新一次宠物UOL修复，也不能仅让玩家更新到1.0.34就宣布问题解决。

该设备样本均加载`6ACA6C26`，与正式1.0.34模块标记/大小一致。22:14:05启动器记录的是“版本与关键文件检查”，通过的是EXE和ijl15.dll，**不等于全部Data IMG逐文件校验通过**。当前本地未提交的Copy保护与资源查询观察代码不能算作玩家当晚已经加载。本轮取得的该设备日志没有`resource_lookup`记录。

## 已检查但不能作为根因的线索

- **整机内存耗尽**：直接按Windows SDK `minidumpapiset.h`解释dump的系统内存及VM计数。近期样本物理内存总量约63.7GiB，仍可用约41.6～42.7GiB，系统提交余量约132～134GiB。没有支持整机RAM或提交上限耗尽的证据。
- **32位进程地址空间**：正式EXE有LAA标志；这批dump仍有约1.7～2.2GiB空闲虚拟区域。低2GiB存在碎片，不能完全排除局部分配失败，但不能说“达到2GiB上限所以必崩”。
- **单纯长时间运行泄漏**：既有运行多小时的故障，也有刚启动约一分钟就失败的新进程；不能单凭在线时间解释全部事件。
- **宠物零帧旧问题**：附件的新进程日志有正常动作帧与Canvas，不能把历史旧构建的零帧错误直接套到此次26次异常。全站另有1个CTerminateException，应独立核对，不能并入其余192个运行作为同一机制。
- **退出码0**：几个进程先记录`_com_error`逃出主循环，随后原生清理并以0退出；0不表示玩家正常主动关闭。最后一个附件进程在导出时还未写最终退出行，仅报告异常已捕获。
- **网络上传失败**：启动器有诊断上传12002/12030/12152等错误，会影响证据及时性；不能代替游戏主线程的COM/访问违例作为退出根因。

## 后续处理顺序
