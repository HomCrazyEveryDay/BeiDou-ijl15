复核两版历史 DLL（PE timestamp `6AC250BF`、`6ABB6245`）内嵌的动作表补丁数组：

- 各 **211 项**与当前 `EvanActionTableRefs.inc` 完全一致，EXE 上每个原操作数均匹配。
- 每项仅写四字节指针，均不覆盖 `0092EDB2..0092EDBB` 的 SEH 序言与 CALL。
- 与这个区域相关的直接地址常量只找到 `0092EDB2`，用于已经识别的远端动作入口；没有发现 `00A60A98` 或 `0092EDB7..0092EDBB` 的直接常量。

因此不能把故障简单归因于“新增动作索引越界”或“动作表指针补丁覆盖 CALL”。这不是对所有运行时计算写入的排除，也不能证明玩家 EXE 内容完整。六次都使用同版 DLL、同角色，只构成关联。

继续需要核对 `0092EDB7` 实际 CALL 是否仍指向 `00A60B98`。若位移 `DC 1D 13 00` 变成 `DC 1C 13 00`，会正好指向故障地址 `00A60A98`；本轮仍没有取得这六次的 dump 来证明该字节变化。

### 为什么补“直接调用者”

原生 `00410FDF` 是不建立 EBP 帧的函数，只有 `push esi`。在 `00410FF5` 出错时：

```text
[ESP]    保存的 ESI
[ESP+4]  直接返回地址
[ESP+8]  IUnknown* 入参
[ESP+C]  AddRef 标志
```

只沿 EBP 链会看到调用者的父函数，漏掉这一个最关键的返回地址。新版报告先校验已复制的故障附近机器码，再从原始 ESP 快照提取 `[ESP+4]`，输出 `directCallerReturn` 与模块/偏移。缺失字节或签名不符明确标为 unavailable；不读取日志写入后的活动栈。

## 后续静态复核：动作现场的栈深度与标志位

唯一 EIP 与 ExceptionAddress 一致的 pid5712 报告保存 `EBP=0019E7F4`、`ESP=0019DBB0`、`EFLAGS=00010293`。两指针相差 `0xC44`，恰好等于父函数 `00950921` 的 SEH 记录 12 字节、局部区 `0xC14`、三个保存寄存器 12 字节、四个参数 16 字节、两层 CALL 返回地址各 4 字节之和。这使 `00951794 → 0092EDB2 → 错误序言入口` 的路径获得第二个独立支持，仍不能证明 CALL 位移实际被改写。

这条路径最后一条影响算术标志的原指令是 `00951778 cmp [ebp-10h],00D7511E`。随后的条件跳转、MOV、PUSH、CALL 与 `mov eax,00ADB788` 均不改变这些标志。独立 x86 探针以三个候选 skillId 执行相同 CMP，随后执行相同解码的 `00 00 / add byte ptr [eax],al`，向只读页触发真实 AV：

| 候选 skillId | 故障 CONTEXT 的 EFLAGS | 算术位（mask 08D5） | 与 pid5712 一致 |
| --- | --- | --- | --- |
| 1311001（枪连击） | 00010293 | 0091 | 是 |
| 1311002（矛连击） | 00010297 | 0095 | 否，PF 不同 |
| 1321003（突进） | 00010293 | 0091 | 是，但该样本 ESI=54 对应 burster2 |

三个探针均捕获预期的写 AV、故障指令和 `0xC44` 栈深度；没有启动游戏。探针用 12 字节占位模拟原生 SEH 记录，并保留测试进程自己的合法异常处理链，并非把游戏原函数整体执行了一遍。结果验证标志位推导及失败的 ADD 不会把 CONTEXT 改成 ADD 成功后的标志。

**条件性结论：** 若所重建的调用路径成立且该 CMP 的运行时代码与基线一致，则在当前已找到的两个 burster2 技能候选中，pid5712 更支持 `1311001`，排除 `1311002`。这不是直接读出的 skillId，也不能外推到另外五份已经回退 CONTEXT 的报告；没有据此修改技能或资源。仍需该次 dump 的栈与代码字节核实。结果保存为 `_diagnostics/crash-followup-20261008/action-flags-probe.json` 与 `deeper-static-audit.json`，探针源码位于 `.tmp/crash-path-probe-20261008/`。

## 后续静态复核：系统写入与场景日志语义

历史四份完整内存 dump（同一 `KERNEL32.dll 10.0.19041.6456`、PE timestamp `869878D1`、SizeOfImage `000F0000`）保存了 `+1EB0B` 的机器码。直接解析其中一份模块导出表，确定 `+1EB00` 为 `InterlockedDecrement`，`+1EB0B` 是 `lock xadd [ecx],eax`；前一条原指令令 `EAX=FFFFFFFF`。这与纸鸢逐风报告的 EAX、ECX 和写地址完全吻合，因此把**对无效或不可写计数地址执行原子减一**提升为优先调查方向。

该证据来自参考系统构建，不是纸鸢逐风的同次模块，仍不能把 API 命名写为已经完全确认；还不能区分悬空引用、重复释放、其他计数器损坏和页面权限异常。保存结果包含原 dump 路径、导出名、版本、逐条反汇编，见 `kernel-code-availability.json` 与 `deeper-static-audit.json`。报告残留 EDI=`00AFD6C4` 对应原生容器的析构 vtable；因上下文已回退，不能由此还原具体拥有者或宣称已经找到释放来源。

另外复核到两处容易误读的线索：

- `showMobDamage.field init` 来自 `BossHP::HookInitField`，钩子实际地址 `00528DBC` 是 `CField::CField`。记录发生在调用原构造函数之前，不是原生 `CField::Init` 完成标记；没有 `activateFromUserUpdate` 只表示尚未观察到对应更新标记。空 variant 崩溃紧邻此日志，不能直接定位到某个地图资源加载函数。
- 空 variant 与 Canvas 样本曾出现的 `00BF6300` 是共用缺省参数 variant。原生 `00A604A6` 将它初始化为 `VT_ERROR=10`、值 `80020004`，不是某个特有的地图或画布对象。共享这个地址不能证明两类故障同源。
