## 1. `00A60A98`：动作调用链中的错误落点

六次均为写访问异常，目标均为 `00ADB788`；相同角色 charId=841，跨五张地图、两个安装标识。两个安装标识不能直接解释成两台机器。

| 客户端自报时间，换算 UTC+8 | run 前缀 | 断线地图 | ESI | 原始 EIP 是否保留 |
| --- | --- | --- | --- | --- |
| 10-05 15:49:29.586 | `7d10c99f` | 550000200 | 61 | 否 |
| 10-05 17:43:17.843 | `3a380121` | 100000000 | 61 | 否 |
| 10-05 21:55:00.725 | `fe6a3e53` | 610010104 | 61 | 否 |
| 10-06 00:54:17.372 | `079303f4` | 100000000 | 54 | 是 |
| 10-06 09:08:26.390 | `1ee4704c` | 270030410 | 61 | 否 |
| 10-06 09:17:41.999 | `1057286c` | 551030100 | 54 | 否 |

在本地 EXE 基线中：

```text
0092EDB2  B8 88 B7 AD 00     mov eax,00ADB788
0092EDB7  E8 DC 1D 13 00     call 00A60B98
00A60B98                    原生 SEH 函数序言辅助代码

00A60A95  E8 B3 4B 00 00     call 00A6564D
00A60A98  00 00             从错误边界解码：add byte ptr [eax],al

00ADB788                    mov eax,00BBE118; jmp 00A60836
```

`00A60A98` 在一条 CALL 的位移字节内部，不是正常指令入口。有效现场 `EAX=00ADB788`、写目标同址，与从这里错误解码并写 EXE 代码页一致。`00ADB788` 是 `0092EDB2` 使用的异常处理代码，不是角色对象或缺失的资源地址。因此“六次写同一地址”很可能是同一路错误控制流的指纹，不能按普通空指针处理，更不能通过让代码页可写掩盖异常。

pid 5712 的 EBP 链可验证到：

```text
窗口消息/输入
→ 0094CD12 → 0094FA2D → 009690BB
→ 0096951E（调用 00950921 后的返回位置）
→ 本地动作/技能处理
→ 错误落点 00A60A98
```

`0092EDB2` 的原生序言尚未建立新 EBP 时，父函数 `00950921` 的帧仍会成为最上层已建立帧。该父函数开始分配 `0xC14` 字节，符合现场 EBP/ESP 的距离。

六次还保留一致关系：`ECX=EBX` 为用户对象，ESI 只出现 54 或 61；EDI 分别为 DLL+`106E00` 或 DLL+`106EA8`，相差 `7×24`。二者减去 `ESI×24` 都得到 DLL+`1068F0`，与项目扩展动作表的 24 字节条目布局、原生 `0095176B` 取表方式吻合。这个额外证据使 `00951794 → 0092EDB2` 比另外 8 个静态调用候选更值得优先核查。54/61 是动作索引候选，不是技能 ID；它们也不是本项目新增的 162–166 动作索引。

源码中未找到对 `0092EDB7` 的显式写入，也没有显式调用 `00A60A98`；本地原 EXE 扫描没有直接 CALL 该错误地址。动作表指针补丁位于 `0095176E`，远端动作观察调用位于 `00980760`，均不能仅凭位置接近就判定有错。旧 DLL 静态信息不能排除运行时覆盖、间接写入或玩家 EXE 内容不同。

**下一步必须检查的现场：** 优先取得 pid 5712 的原始 dump：`ijl15-crash-20261005-150958839Z-pid5712-tid1240-codeC0000005-addr00A60A98.dmp`。读原始 ESP 的返回地址、`0092EDB2..0092EDBC` 和 `00A60A90..00A60BC0` 的实际字节、父帧中的技能/动作参数及加载模块。若 `0092EDB7` 的 CALL 位移从 `DC 1D 13 00` 变为 `DC 1C 13 00`，它恰好会少跳 `0x100`；这是可证伪的核查点，目前没有证据证明这一字节已被改写。修复应作用于错误写入/跳转的来源，不能在 `00A60A98` 做吞异常补丁。

## 2. `0066B5B1`：怪物移动对象初始化回调

本次 run=`52bdd31b590ca704e2876e0ff1bc86be`，地图 270020500。客户端自身时间线：

1. 20:04:02.701，死亡弹窗创建，HP=0。
2. 20:04:03.825，关闭弹窗。
3. 20:04:04.468，场景初始化；随后仍处于用户对象切换阶段。
4. 20:04:04.512，连续收到 `0x00EE`，记录尺寸 11、91；`SendOpcode.SPAWN_MONSTER_CONTROL`。
5. 20:04:05.608，未处理异常；20:04:05.920 完成文本报告。

断线记录 HP=50，说明服务端已进入复活后状态。保存的 EIP=`00679355` 正好是分发 `0xEE → 00679777` 后的位置，支持正在处理怪物控制封包，但不是原始崩溃 EIP。

直接故障机制：

```text
0066B59C mov eax,[ecx+118h]
         空接口转换为其原生对象指针，空值仍为 0
0066B5B1 cmp dword ptr [edx+250h],0
```

报告 `EAX=FFFFFFF4`、`EDX=0`、访问地址 `00000250`。不能将 ECX 简称“完整 CMob 基址”：构造函数把 `00AF824C` 虚表放在 `CMob+4`，该回调接收的是这个子对象，故回调 `[ECX+118h]` 实际是 `CMob+11Ch`。

### 历史 dump 的可复核机制

本地既有样本：`_diagnostics/crash-users-20260908/reverse-rar/BeiDou_20260831_174602_pid14476_tid9244_codeC0000005_addr0066B5B1.dmp`。这是不同时间的辅助证据，不冒充本次 dump。其故障位置机器码与当前 EXE 基线相同。

- CMob 基址 `3724F3DC`，回调 this=`3724F3E0`，子对象虚表=`00AF824C`，slot+4 指向 `0066B599`。
- `CMob+118h=2E3392E0`，第一移动对象接口已存在；转换后的原生对象为 `2E3392D4`。
- `CMob+11Ch=0`，第二移动对象尚未创建；这正是回调实际读取的字段。
- 第一对象的 owner=`3724F3E0`，与回调 this 相符。
- 从残留栈字节恢复并逐个核对原程序返回位置：

```text
00679777 处理怪物控制封包
→ 00678308 创建本地尚不存在的怪物
→ 00662884 初始化怪物
→ 00662A2F 调用第一移动对象的初始化虚函数
→ 009BBD3D → 009B12A8
→ 009B13E4 调用 owner 虚表 slot+4
→ 0066B599 → 0066B5B1
```

该链来自剩余栈内容，而不是完整的异常 CONTEXT；最后一段 EBP 被复用为怪物 OID，不能继续当帧指针遍历。中间返回地址和对象关系互相吻合。

原生 `00662A55..00662A67` 才创建并设置第二移动对象，位于上述回调之后。`009B13BD` 在 `(action & ~1)==0` 时触发这次 owner 回调；历史帧中 action=1。这解释了为什么不是每次刷怪都崩溃。服务端新 Monster 默认 stance=5，但移动处理会更新 stance，控制/生成封包直接序列化 `life.getStance()`，因此交接一个已运动怪物时有必要核对实际 stance。不能只因首个 EE 尺寸较小就判断封包截断；停止控制包本来就是短格式。

**修复方向：** 在明确的初始化回调阶段处理尚未建立的第二移动对象，或调整创建/初始化顺序，同时保留正常移动和后续控制权切换。不要直接把所有怪物 stance 改成 5，也不要把死亡弹窗、地图资源当成既定病因。本次尚缺 EE 正文的 OID、模板、stance 和同一链的原始栈；现有文本仅记录 opcode/长度。历史机制有较强证据，本次属于同机制的判断仍需复核。

## 3. `00410FF5`：空 COM 对象的 AddRef

run=`218dc88f4b18e7cda7d04e84df4c8c38`，梨涡允允，断线地图 910000000。客户端 12:04:19.204 场景 init、19.320 dispose、19.409 activate；21.735 记录异常，22.072 完成报告。不是刚开始读取地图的唯一瞬间，场景已激活约 2.3 秒。

`00410FDF` 接收 IUnknown 指针和是否 AddRef 的参数，设置 variant 类型 13（VT_UNKNOWN），保存指针；第二参数非零时：

```text
00410FF5 mov ecx,[eax]   ; EAX=0
00410FF7 push eax
00410FF8 call [ecx+4]    ; IUnknown::AddRef
```

故障对象是传入的 COM 接口指针，不是 variant 输出地址本身。该通用函数在 EXE 可执行节中有 397 个直接 CALL 字节候选，分布于地图、人物动作、UI 等大量路径；这个数量是静态候选扫描，不等于已逐一恢复 397 个调用函数。

最后封包包含人物生成、NPC 显示/控制、宠物、队伍信息和 buff，仅凭“刚进自由市场”无法区分背景、其他玩家装扮、技能效果或 UI 的空对象。EIP/EBP 已退到 ntdll 顶层，不能从现有报告恢复上游资源名。与 `00A60A98` 同角色只构成关联，尚无共同根因证据。

**下一步：** 取得本次原始栈或定点首次异常快照，恢复 `00410FDF` 调用者、两个入参、返回地址，以及上游 COM/HRESULT/资源路径。修复应在错误生产空对象的路径上完成；全局把 null variant 默默变为成功可能只是把故障推迟到下游。

## 4. `CANVAS+ED28`：空源画布，既有防护确已安装

run=`68439cf9400c35a777341e334676ea93`，勇气，断线地图 910000001。当次完整 trace 的第 3 行明确为：

```text
2026-10-05T17:04:28.442Z category=resource.guard install avatar=1 item=1 statusbar=1
```

该运行使用旧版 DLL `6ABB6245`，但已包含并成功安装 `008DA50B` 状态栏左括号的定点补丁。全份对应 trace 只有这一条 resource.guard 安装记录，没有 `statusbar missing_canvas` 恢复事件。因此不能解释成“忘记安装上次防护”；也不能因无恢复日志就排除后来代码覆盖等尚未观察到的情况。

与项目 CANVAS 基线比较：

```text
CANVAS+ED21  接收 ECX，保存到 ESI
CANVAS+ED28  mov eax,[esi]       ; ESI=0，读取 0
CANVAS+ED2F  call [eax+40h]
```

Canvas 复制路径在 `CANVAS+D5FE` 把其源接口参数传给这一函数，符合“对空源画布取属性”的机制。但本次栈已丢失，未验证玩家 CANVAS 完整哈希，不能锁定复制调用者，更不能锁定资源路径。旧船长案例证明的是 `008DA50B`，不代表所有 ED28 都来自那里。

### 时间线纠正

不能拿客户端 UTC 字符串直接与服务端时间相减。该运行最近五次连接的绑定往返记录显示，客户端相对服务端约快 `28.748–28.759` 秒（含网络/处理耗时，仅作近似校准）。

- 未校准文本报告：客户端 21:02:58.082。
- 未处理异常入口：客户端 21:02:56.569。
- 按最近一次 28.748 秒校准：入口约服务端 21:02:27.821，文本报告约 21:02:29.334。
- 服务端断线：21:02:29.976。

这与“先异常、随后断线”相容。完整封包环形记录最后一条为客户端 21:02:55.411，距离异常入口约 1.16 秒。trace 的低频收包活动每分钟汇总一次，不能把最后的 21:02:30.480 汇总当成最后收包时间。没有证据支持“断线后卡住 28 秒才崩溃”。

**下一步：** 首次异常栈恢复具体 EXE/DLL 调用者、复制源/目标画布接口及其资源来源。既有状态栏防护不扩大到整个 Canvas DLL，不凭此修改或重建 IMG。

## 5. `KERNEL32+1EB0B`：切图期间的无效写目标

run=`87d488625fa359c359a1edff44d33fcd`，纸鸢逐风，地图 240040510。异常写目标 `248B3120`，报告保存 `ECX=248B3120`、`EAX=FFFFFFFF`；异常模块基址 `77080000`，地址 `7709EB0B`。

服务端 `lastRecvOpcode=38` 是十进制，等于 `0x26 CHANGE_MAP`，不是 `0x27 CHANGE_CHANNEL`。当时 `inTransition=true`、`serverTransition=true`，可以确认地图切换上下文。客户端绑定时间相对服务端约慢 4.5 秒，不能按未校准的跨机器时间差决定因果。

这份报告 `crashTraceEnabled=false`，仅约 1.3 KiB，没有 recentEvents/recentIncomingPackets；EIP 已位于 ntdll，唯一 EBP 帧返回 0。异常不是“写入空地址”，而是写入非零、当前不可写的地址。

报告没有玩家 KERNEL32 版本、PE timestamp/size、PDB 标识或该位置字节。Windows 不同版本同一模块偏移可对应不同代码，不能用本机 KERNEL32 的 `+1EB0B` 直接命名 API。也不能仅凭崩在系统模块，推定应重装系统或替换 DLL。

**下一步：** 同次 dump 的模块清单、原始调用栈、fault 附近代码、`248B3120` 的内存区属性及调用参数。由此区分引用计数/同步对象生命周期、已释放指针、上游内存破坏等候选；目前不能排序到某一具体 API。
